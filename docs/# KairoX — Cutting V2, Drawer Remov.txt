# KairoX — Cutting V2, Drawer Removal & Store Merge, then the backend bug list

## Context

Three things are being asked for, from two documents and your notes:

1. **Cutting V2.** Kumar keeps the real cutting record in Excel (sheets, DCM per sheet, returns,
   adjustments) and re-types the finished bundle into the ERP. Two systems, double work, and the
   ERP cannot say how much leather was actually consumed. V1 only starts recording once the bundle
   is already cut.
2. **Drawers must go.** There are only 200 physical drawers. A style releases 100+ pieces, stalls
   mid-chain, and the next 50 pieces have nowhere to go; re-allocating by hand is too complicated
   for the DM. The drawer is a bottleneck that earns nothing. Store merge should be leather +
   lining + the right accessories, scanned off the piece barcode, and it must be easy.
3. **~20 backend fixes** from the bugs PDF, plus outsourcing tracking.

**Sequence you chose: Cutting V2 + Drawer/Store first, then everything else.**

### What the exploration changed about the approach

The codebase is further along than CLAUDE.md describes, and three findings make this much cheaper
than it looks:

- **`STORE` is already a derived display concept**, not a stage. `core/store_display.display_stage()`
  computes it from (last event, drawer state). Removing the drawer means repointing that one
  function at a piece-level state — not inventing a store.
- **`core/kit_rules.drawer_complete()` is not really about drawers.** It takes
  `leather_in / lining_in / accessories_in / needs_lining / kit_required` — all facts about the
  *garment*. It becomes `piece_complete()` with the same three clauses.
- **`style_material_spec` already has a `size` column and a kit ledger that already tolerates a
  NULL drawer** (`piece_material_issue.drawer_id` is nullable and already written as
  `drawer.id if drawer is not None else None`).

### The one thing that must not be missed

**`_merge_ok` is the ONLY gate on LINE_STITCHING.** `_sequence_ok` returns `True` early for it
(`production/service.py:162`, `prev is None`, because `LINE_STITCHING.predecessor()` returns None by
design). Delete the drawer without replacing the gate and **line-stitching becomes completely
ungated** — any piece could be stitched before it was ever cut. The replacement gate is not
optional cleanup; it is the first thing to write.

## Decisions locked (from your answers — do not relitigate)

| Question | Decision |
|---|---|
| What is a leather sheet | One physical hide. **Each gets its own barcode** (MD's requirement). 7-12 per garment. |
| What is one cutting-sheet row | **ONE garment** (one piece). |
| Can a sheet span rows | **No** — a sheet is fully consumed by the row it is issued to. Status, not balance. |
| When stock decrements | **At production log, as today.** Approve reserves; logging consumes. |
| Auto-allocation target | Style spec DCM when it exists, else a **built-in size→DCM baseline** (below). Manager edits every cell regardless. |

| Outsourcing | Dispatch + return ledger per piece, with the vendor record shaped so rates can be added later. |

### The size → DCM baseline (researched, and checked against your own sheet)

You said the DM is not asked for per-piece DCM, so the system needs a sensible default. Validated
against your screenshot: all six rows average **46 dcm per hide** (43-63 range), and the leather
trade puts a jacket at 45-55 sq ft = 418-511 dcm. Both agree.

| Size | Target dcm | ≈ sheets @46 |
|---|---|---|
| XS | 340 | 7 |
| S | 370 | 8 |
| M | 400 | 9 |
| L | 430 | 9 |
| XL | 465 | 10 |
| XXL | 500 | 11 |
| XXXL | 540 | 12 |

Italian numeric sizes map onto the same ladder (46=XS, 48=S, 50=M, 52=L, 54=XL, 56=XXL, 58+=XXXL).
This lives in a new `app/core/leather_norms.py` beside `kit_rules.py` / `lining_rules.py`, as a pure
table with the reasoning written down. **It is explicitly an estimate** — the style's
`style_material_spec` leather `qty_per_piece` wins whenever it exists, and the manager edits the row
either way. Note your screenshot rows run 5-7 sheets / ~290 dcm, below the 7-12 you quoted; the
baseline sits between the two, which is what "near enough, then edit" means.

# PHASE 1 — Cutting V2 + Drawer removal + Store merge

## 1A · Leather sheets on the material side

**New table `material_sheet`** — child of `material_lot`, because "one lot per spec"
(`materials/service.py:130-153`) forbids a second lot for the same article/colour/thickness, so a
sheet cannot be a lot.

```
material_sheet
  id, material_lot_id (FK, CASCADE)
  code            "LS-000123"  (its barcode)
  dcm             Numeric(12,3)   the measurement written on the hide
  status          IN_STOCK | ALLOCATED | ISSUED | CONSUMED | RETURNED | SCRAPPED
  cutting_row_id  FK, nullable    which garment it went to
  received_at, consumed_at
```

- **New `BarcodeType.LEATHER_SHEET`** (`core/enums_barcode.py:331`) and a new nullable
  `barcode_registry.material_sheet_id` FK — the established polymorphic-by-type pattern.
- **`barcode/service.py:83`** — the three lot types currently fall through one
  `elif row.material_lot_id:` branch. Add a `material_sheet_id` branch before it, returning the
  sheet + its parent lot.
- **`mint_lot_code_nocommit` assumes 1 barcode per lot** (`barcode/repository.py:376-383`) and
  retirement uses `.limit(1)` on `material_lot_id` (`barcode/service.py:440-445`). Sheets get their
  own mint/retire path; do not widen the lot path.
- **`lot.on_hand` stays the leather stock figure in dcm** and remains the thing
  `_decrement_nocommit` moves. Sheets are the detail beneath it; a consistency check
  (`Σ IN_STOCK sheet dcm == on_hand`) is reported, not enforced, so a mismatch is visible rather
  than blocking receiving.

**Receiving**: `POST /materials/receive` gains an optional `sheets: [{dcm}, …]` list. Supplying it
mints that many sheet rows + barcodes and returns the codes for printing. This is also bugs **#6**
(piece/sheet count for leather), **#7** (stop abusing `thickness` for sheet count) and **#18**
(total sheets in the lot directory).

## 1B · The Excel-style cutting sheet

**New module `app/modules/cutting/`** (models, schemas, repository, service, router) — it is a new
bounded concept, not an extension of production.

```
cutting_row                       ONE GARMENT
  id, piece_id (FK, nullable until bound)
  style_id, sku_id, colour, article, size, rc_no
  cutter_employee_id
  work_date
  status         DRAFT | APPROVED | LOGGED | CANCELLED
  target_dcm     what the allocator aimed at
  total_dcm      DERIVED from its sheets, never typed
  approved_by, approved_at
```

Sheets attach by `material_sheet.cutting_row_id`, so "the sheets on this row" is one indexed read
and a sheet can never be on two rows.

**Endpoints** (`/cutting`, roles CUTTING_MANAGER + DM + MD):
- `GET /cutting/sheet?style_id=&colour=` — the grid. Style + colour chosen at the top and applied
  to every row, as in your Excel.
- `POST /cutting/rows/generate` — creates one DRAFT row per un-cut piece of the selected
  style+colour and **auto-allocates sheets** (§ baseline above) from IN_STOCK sheets matching the
  article + colour, nearest-fit first, until the running dcm reaches the target. Allocated sheets
  go to `ALLOCATED` so two rows cannot claim the same hide.
- `PATCH /cutting/rows/{id}` — edit any cell: cutter, size, rc_no, article, colour.
- `POST /cutting/rows/{id}/sheets` / `DELETE …/sheets/{sheet_id}` — **the cutter-needs-one-more /
  one-less flow you described.** Removing returns the sheet to `IN_STOCK`; adding takes it from
  stock. Free and unaudited while DRAFT.
- `PATCH /cutting/rows/{id}/sheets/{sheet_id}` — correct a sheet's DCM.
- `POST /cutting/rows/{id}/approve` — the gate.

**Approval** follows the existing audited-transition pattern exactly (`ProductionReleaseStatus` +
`BreakdownService.release_styles`, `imports/breakdown.py:590-749`): a status enum, an actor, a
timestamp and an `AuditLog` row. Two new `BarcodeAuditAction` members
(`CUTTING_ROW_APPROVED`, `CUTTING_ROW_REOPENED`).

> **Trap:** `AuditLog.actor_user_id` FKs to `app_user.id`. Pass the **login's** id, never the scanned
> `employee.id` — that exact mistake produced a 500 in the store scan
> (`drawers/service.py:572-584`). The worker goes in the `after` payload as data.

On approve: sheets move `ALLOCATED → ISSUED`, `total_dcm` is frozen, the row becomes read-only.
Any later change is a reopen (audited) — matching your "edit freely before approval" instinct while
keeping the money path honest.

**Attendance**: the grid shows who is present today via the existing
`AttendanceService.today_roster()` (`attendance/service.py:420`), so the manager picks only cutters
actually in the factory — your "check attendance in the cutting dashboard, not the production
logger".

## 1C · Production Logger retrieval

`POST /production/log` is unchanged in shape. When a cut scan resolves a piece that has an
**APPROVED** cutting row, the router pulls `article`, `colour`, `lot`, `total_dcm` and the sheet list
from that row instead of requiring them on the request. The service still does the single
per-batch decrement it does today (`production/service.py:510-531`) — **stock timing is unchanged,
as you chose.** On success the row goes `APPROVED → LOGGED` and its sheets `ISSUED → CONSUMED`.

This is also bugs **#23** and **#27** (article & colour auto-filled on piece scan) and **#30**
(per-piece DCM at sheet issue), and **#17/#28** fall out of it: DCM spend per piece is now the sum
of real hides.

A piece with no approved row keeps today's typed path exactly, so nothing on the floor breaks
mid-migration.

## 1D · Drawer removal → piece-level store state

**Move the store state from the drawer onto the piece.** Five columns on `piece`:
`store_state`, `leather_in`, `lining_in`, `accessories_in`, `store_entered_at`.

**Migration**: copy `drawer.state / leather_in / lining_in / accessories_in` onto the piece it
currently holds, via `drawer.current_piece_id`. Nothing in flight is lost. The drawer tables stay,
unwritten, for audit.

| Today | Becomes |
|---|---|
| `DrawerState` (7 values) | `StoreState`, same 7 values, on the piece |
| `kit_rules.drawer_complete()` | `kit_rules.piece_complete()` — identical clauses |
| `store_display.display_stage(drawer_state=…)` | `display_stage(store_state=…)` |
| `DrawerService._needs_lining` / `_needs_lining_map` | **Relocate to a store service — do not delete.** Production calls them at `service.py:221, 711, 1011`. |
| `_merge_ok` reads `drawer.state == SENDED` | reads `piece.store_state == SENDED` — **write this first** |
| `POST /drawers/store-scan` (employee → drawer → piece) | `POST /store/scan` (employee → piece) — **one scan fewer; this is the "make merging easy" fix** |
| `POST /drawers/send` | `POST /store/send` (piece ids) |
| `release_nocommit` at PACKAGE_EXPORT | clears the piece's store flags; no pool to return to |
| `STORE_MANAGER` role | kept, repointed at `/store` |

**Premint** (`imports/premint.py`) loses `_build_drawer`, `_PoolAllocator`,
`bootstrap_drawer_pool`, `allocate_waiting_pieces`, `grow_drawer_pool`, `drawer_pool_status` and
`INITIAL_DRAWER_POOL`. The four-phase flush collapses to two — phases 1 and 3 existed *only* for the
piece↔drawer FK cycle. **`pieces_waiting_for_drawer` disappears from four user-visible places**
(breakdown upload response, release router, `/drawers/pool`, analytics `no_drawer` bucket) — that is
the bottleneck you are removing, so it should vanish, not be renamed.

**Also resolved:** bug **#15** (a separate page to find a piece) becomes trivial — there is no drawer
to look up. `GET /store/pieces/{code}` already exists and needs only a wider role set so the person
placing pieces can use it without DM access.

Analytics and dashboard read drawer state in ~30 places (`analytics/service.py:216-276`,
`dashboard/repository.py:1299-1645`). These are mechanical: swap the join to `piece.store_state`.
The `_STORE_STATES` label table and the store KPIs keep working unchanged.

## 1E · Easy merge + size-matched accessories

**The merge scan**: scan employee, scan piece. The response already carries the kit checklist
(`material_requirement_block`) — it now returns **only the accessories that match this garment's
size**, and confirming issues them and decrements stock (which
`issue_kit_nocommit` already does). That is your "scan the piece barcode and it tells you what
accessories to merge".

**Bug #10 — the size-matching bug. Root cause found.**
`StyleSpecService.merge_lines` (`materials/style_spec_service.py:206-235`) keys lines on
`(category, subtype, article)` and **never reads `SKU.size`**. All four consuming surfaces
(`kit_required_for_piece`, `kit_by_pieces`, `material_requirement_block`, `issue_kit_nocommit`) go
through it, so one fix corrects all four. Today a DM entering Thread S / M / L gets either all three
on every piece (distinct articles) or silently only the last one (same article, distinct size).

**The fix needs a new column, not the existing one.** `style_material_spec.size` means the
*material's* size (`models.py:380`: "zip 60cm, button 18L"). Overloading it would be a trap. Add
**`garment_size`** — "this line applies only to garments of this size; NULL = all sizes" — then:

- add `garment_size` to `merge_lines`'s key tuple and filter by the piece's SKU size
- when the DM adds an accessory line whose material `size` is a garment-size token (S/M/L/XL/XXL,
  or 38-62), **default `garment_size` to it**. That gives your "zip size L automatically merges to
  the L piece" with no extra data entry.

> Note: `THREAD` has no `size` field in `MATERIAL_SPEC` at all
> (`core/enums_barcode.py:439-442` — it takes `thickness` + `mtrs`). So the Thread S/M/L case must
> be expressed through `garment_size`, which is exactly what the new column is for.

> Watch: spec rows are frozen after release (`_assert_editable`), but the *effective* recipe is
> computed at read time, so this fix changes what already-released styles resolve to. That is the
> intent — it is the bug being fixed — but it must be called out in the release notes.
