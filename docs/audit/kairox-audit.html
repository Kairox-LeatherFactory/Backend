Read-only audit · Phase 1 · no application code modified

The backend does not currently start, and the schema cannot be built.

A fifteen-pass audit of app/core and eleven scoped modules, three days before a production deploy. 132 findings, every one cited to a file and line.

Audited 2026-07-30 Deploy target 2026-08-02 Tree 55ca2ea + 24 modified, 8 untracked Findings 132 Blockers 15

Three independent reasons this cannot deploy today

These are not code-quality opinions. Each was verified by reading the file; the first two were additionally confirmed by executing the import.

  1. The application cannot be imported. app/main.py:92 imports app.modules.attendance.barcode — that module does not exist. app/modules/imports/router.py:31 imports load_preview, which is commented out at app/modules/imports/load_to_db.py:83. Either one alone stops uvicorn at startup.
  2. The schema cannot be created by Alembic. alembic/versions/20260724_01_july28_fixes.py:10 ships the literal placeholder down_revision = "<CURRENT_HEAD>", and fiber_role_bom_item.py declares down_revision = None, creating a second root. alembic upgrade head fails on both counts. Today the only path that produces tables is create_all() under DEBUG=true (app/main.py:145-147) — a dev convenience, not a production migration.
  3. Payroll can pay the same fortnight twice. A closed wage run can be recomputed (app/modules/wages/service.py:329-336 has no status guard), wage_line carries no UNIQUE(wage_run_id, employee_id), and a run that crashes mid-population leaves committed money rows at status=OPEN, invisible to the duplicate-run check that filters on CLOSED.

What this audit is

Fifteen passes over app/core plus users, wages, analytics, employees, attendance, drawers, barcode, production, clients, materials, imports, run in the severity order specified in the brief. bom, procurement, inventory and supplier_po were not audited; where a scoped module touches them the seam is recorded as a finding and the import was not followed.

Every finding carries a severity, an owning module, a file-and-line citation, and a deadline tag. Nothing was fixed. No file under app/, alembic/ or scripts/ was modified.

Counting note. The pass sections contain 139 finding entries; seven of those are cross-references of a finding already recorded in an earlier pass, marked as such and excluded from every count on this page. 132 distinct findings.

Why core dominates. Thirty-six of 132 findings sit in app/core and alembic/, and they are disproportionately the severe ones. That is the audit's central structural result: most module-level bugs in this codebase are downstream of two core decisions — a star-import that silently replaced the production stage vocabulary (F01), and a migration chain that was never rebased (F59, F60). Fix those two and roughly a dozen module findings resolve themselves.

Top 10, ranked

Ranked by what stops the deploy first, then by money at risk, then by data exposure. All ten are D0.

  1. The application cannot be imported

    Three independent failures at startup: two dead imports at app/main.py:92 and app/modules/imports/router.py:31, plus a supplier table declared twice in one metadata registry (barcode/models.py:154 against supplier_po). Nothing else on this list matters until all three are gone. BLOCKER F00, F104

  2. Alembic cannot build the schema

    A literal "<CURRENT_HEAD>" placeholder at 20260724_01_july28_fixes.py:10 plus a second root at fiber_role_bom_item.py. You currently have no repeatable way to create a production database. BLOCKER F59, F60

  3. A closed payroll run can be silently recomputed

    wages/service.py:329-336 goes from get_run straight to clear_lines with no status check. Four separate docstrings assert the run is frozen; nothing enforces it. BLOCKER F20

  4. An interrupted payroll run pays the fortnight twice

    _populate_run spans four commits, and overlapping_closed_run (wages/repository.py:189) only sees CLOSED runs. A crash after add_lines leaves committed money at OPEN, invisible to the duplicate check. BLOCKER F22

  5. Nothing enforces one wage line per employee per run

    wage_line has no __table_args__ (wages/models.py:99-105); the baseline migration creates both indexes unique=False. The invariant lives in an in-memory defaultdict. BLOCKER F21

  6. Production JWTs may be signed with the shipped default key

    core/config.py:123 defaults secret_key to "dev-only-insecure-change-me-in-prod". A missing .env boots happily and mints forgeable tokens for every role. BLOCKER F32

  7. A client login can read another client's orders

    Six analytics endpoints fetch by id with no tenancy predicate, while only clients/router.py:57-58 and analytics/router.py:36 scope correctly. A client reads their own order list, then substitutes a competitor's id. BLOCKER F33

  8. Any employee can read the whole floor's attendance

    GET /attendance/today is defined twice (attendance/router.py:128 and :171). The bare get_current_user definition wins; the role-gated one is unreachable, and attendance is not behind block_employees. BLOCKER F35, F49

  9. The geofence is bypassed by not sending GPS

    attendance/service.py:170-172 skips the fence entirely when lat/lon are absent and records distance_m = 0.0 — identical to standing at the gate. BLOCKER F34

  10. Every production scan 500s against a seeded database

    scripts/seed.py:97-104 seeds operation codes that no longer intersect the live ProductionStage enum, so production/service.py:218-222 raises. The test suite seeds the correct codes and never sees it. BLOCKER F02

BLOCKERproduction D0 production/service.py:279-289, :315-321 · models.py:97

F03 · A re-posted cut scan writes duplicate events and decrements stock twice

Issue
Three facts compose. ProductionEvent (models.py:97) declares no __table_args__ and therefore no UNIQUE(piece_id, operation_id). Rework is detected at service.py:279 and then skips both gates (:281-289). And the rework piece is still appended to logged at :308, which is what the batched stock decrement multiplies by at :319.
Why it's wrong
Permissive rework is deliberate and correct — pieces genuinely go back through stages. But "no unique constraint" plus "skips validation" plus "counts toward consumption" means an operator double-tapping silently consumes leather twice. materials/service.py:259-261 asserts the opposite in a comment: "A re-posted identical scan is caught upstream by the per-piece 'already logged' check." No such check blocks it — has_event_at_op classifies the scan as rework, it does not reject it.
Correct behavior
Rework stays permissive for the event stream, but material consumption is idempotent per (piece, operation) — reworking a piece must not re-consume the hide it was already cut from.
Fix sketch
service.py:316 if is_cut and logged:
        :319 - total = float(consumption_qty) * len(logged)
              + total = float(consumption_qty) * len([p for p in logged if p not in rework])

Primary Exclude rework pieces from the consumption multiplier — the smallest change that makes stock correct without touching the permissive event model. Risk If a rework recut genuinely consumes fresh hide, this under-counts; confirm with the cutting manager which meaning the floor uses. Fallback Add an explicit consumes_material: bool to the scan payload, defaulting to false on rework, so the operator declares it.

Defaults give five connections plus ten overflow per process. Method & limits

What was done

  • Every .py file in the eleven scoped modules and app/core was read in full — roughly 6,800 lines across the scoped set, plus the 17 Alembic revisions, scripts/seed.py and tests/conftest.py.
  • Route tables were built by introspecting each APIRouter's registered dependencies rather than by reading decorators. That is the only reason F35's shadowed route was found — the source reads as though the gate applies.
  • The two boot blockers and the class MRO in F84 were confirmed by executing the import, not inferred.
  • The migration graph was reconstructed by extracting revision and down_revision from all 17 files and following the edges.

What limits this audit

  • The application does not run, so nothing was verified against a live server. There are no reproduction steps involving HTTP requests in this report, and none should be inferred. Every claim is static analysis plus targeted import probes.
  • The working tree is uncommitted and moving — 24 modified files and 8 untracked paths on top of 55ca2ea. Line numbers are accurate as of 2026-07-30 and will drift.
  • bom, procurement, inventory and supplier_po were not audited. Where a scoped module touches them the seam is reported (F104, F126) and the import was not followed. Findings inside those modules are unknown, not absent.
  • Severity is judged against the Aug 2 deploy, not in the abstract. Several D2 findings would be HIGH in a system serving ten factories today.
  • No runtime security testing — no fuzzing, no dependency CVE scan, no penetration testing. The security pass is a code review.
